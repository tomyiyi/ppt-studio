## 第 18 轮（2026-10-01）：hssh 命令里 heredoc 写多行代码报 `unexpected EOF`

**现象**：在 `~/workspace/bin/hssh omarchy '...'` 的命令字符串里用 `cat > file << "PYEOF"`
写 Python 多行文件，bash 报 `line 172: unexpected EOF while looking for matching ''`
（exit 2），文件没写进去。Python 内容里肉眼无未闭合单引号。

**根因**：hssh 命令字符串本身要经过多层 quoting（本地 shell → hssh 脚本 → ssh →
远端 bash -c），heredoc 分隔符与内容里的引号/转义在某一层被提前消费或改写，
导致远端收到的脚本结构损坏。属"多层 shell 转义"类问题，与 Python 内容无关。

**定位过程**：第一次失败后检查 Python 源码无单引号问题；确认不是文件内容问题，
而是传输层 quoting 问题。

**最终解法**：本地用文件工具写好文件 → `base64 -w0` 编码 → 通过 hssh 命令
`echo $B64 | base64 -d > 目标路径` 落盘。base64 字母表无引号/转义字符，
对多层 quoting 免疫。两次传输（scripts + tests）均一次成功，
附带 `python3 -c "import ast..."` 做语法校验。

**经验**：凡经 hssh 传多行文本，一律走 base64 管道，不再用 heredoc。
（工具链坑，非仓库代码坑；GitHub/全网搜索不适用——属本环境特定用法。）

## 第 19 轮（2026-10-01）：Chromium 经 Playwright 在 1920×1080 下截图必现 renderer 崩溃

**现象**：`render_svg.py`（Playwright `page.set_content` + `page.screenshot`）在
omarchy 上渲染 1920×1080 的 SVG 必现 `TargetClosedError` / `Target crashed`；
800×300 viewport 下同样代码、同样图片全部正常。第 17 轮曾二分 9 步未定位。

**定位过程**（对照实验，全部实跑，约 15 次崩溃复现）：
1. 合成小图（800×600 纯色 JPEG/PNG，800×300 viewport）：全过。
2. 真实项目图（1024×1024 照片，800×300 viewport）：全过且像素正常。
3. 真实 `02_colour.svg`（2 张大 JPEG：2667×4000 + 1920×2880）经 `render_one`：
   **复现** `TargetClosedError: Page.set_content`。
4. 控制变量二分（固定 1920×1080 viewport，只变源码像素尺寸/内容复杂度，
   每组 ×2）：**全部崩溃，连 800×600 小图都崩**——当时判定"崩溃与图片内容无关"。
5. `chromium --headless --screenshot` 直接跑同样 HTML（2MB data-URI，1920×1080）：
   **一次成功**（865KB PNG，stddev 83.4 真实像素）——当时判定"渲染器本身没问题"。
6. Playwright `DEBUG=pw:browser` 抓到浏览器侧 stderr：
   `viz.mojom.CopyOutputResultSender` 消息被拒 +
   `GPU process exited unexpectedly: exit_code=9`；
   启动参数含 Playwright 硬编码的 `--enable-features=CDPScreenshotNewSurface`。
7. 当时宣布的"决定性结论"：**崩溃因子是 viewport/截图尺寸，不是图片**。

**反转（对抗式审查）**：宣布结论后做了真正的证伪实验——清理环境后，
在**同一台机器、同一 1920×1080、同一 `02_colour.svg`** 上强制
`--engine playwright` 连跑 **3/3 全部成功**（每次约 2 秒，无崩溃、无僵尸进程）。
"viewport 决定性结论"被**证伪**。

**修正后的根因**：环境资源耗尽，而非 viewport。
- omarchy 的 `/tmp` 是 5.9G tmpfs，被此前各轮遗留的陈旧产物塞到 **80%**
 （`p1-*-clean` ×5 ≈ 2.2G、`nyanpasu-inspect` 384M、`agnes-*` 541M，
  均为 9 月 27–30 日旧会话残留）；chromium 的 disk-cache/crashpad 写
  `/tmp` 开始报 `Failed to write the temporary index file`，CLI 引擎从"一次成功"
  退化为"写出 PNG 但进程永不退出"（subprocess 超时），极端时启动即 abort（rc=134）。
- 每次崩溃的 playwright 运行都会泄漏一整个 browser 进程树（`b.close()` 在
  `set_content` 先抛异常时执行不到——探针脚本之过，`render_svg.py` 本体有
  finally 保护）；实测曾堆积到 **35 个 chromium 进程 / 3.2GB RSS**，
  进一步加速后续崩溃。
- 所谓"viewport 决定论"是混杂偏倚：小 viewport 单次运行资源占用少，
  在已退化的环境里恰好能活下来；第 6 步"决定性"二分实验本身就跑在一台
  已被僵尸进程 + /tmp 压力污染的机器上。viz/GPU `exit_code=9` 是
  renderer 被环境杀死的下游症状，不是病因。

**最终解法**（保留，双引擎降级）：
- `scripts/render_svg.py`：`_build_html()` 抽取；`render_one_cli()` 经
  `chromium --headless --screenshot`（独立 `--user-data-dir` 隔离用户桌面
  Chromium 的单例锁/9222 端口争用；PNG 魔数 + 最小体积校验；原子落盘）；
  `_render_page(engine="auto")` 默认 playwright 优先、失败 warn 后自动降级 CLI；
  CLI 新增 `--engine {auto,playwright,cli}`。
- 在环境退化期间实测：auto 链路正确打印
  `[warn] playwright 引擎失败 (TargetClosedError)，降级到 chromium CLI`
  并切换引擎——**降级机制本身被验证有效**，作为纵深防御保留。
- 另加 `_warn_if_tmp_full()`：`/tmp` 使用超 85% 时打印告警（只告警不阻断）；
  本轮从 `/tmp` 清理出约 3.5G 陈旧产物（保留 `newapi-good.tar` 等可能有用的）。
- `tests/test_render_svg.py` 新增 10 用例（TestBuildHtml / TestRenderOneCli /
  TestRenderPageEngine，全部 mock 不启动真实浏览器）。

**附带坑**：
- `pkill -f "chromium --headless"` 写在同一条 hssh 命令里会把自己杀掉：
  pkill -f 匹配整条命令行，而命令字符串后半段的字面量 `chromium --headless`
  会被自己的 pattern 命中。教训：kill 与被 kill 目标字面量绝不同行；
  或用 `chr[o]mium` 括号技巧且确保命令行别处无字面量。
- `subprocess.run(capture_output=True)` 等待的是**所有继承了管道 fd 的进程**退出；
  chromium 的 crashpad/zygote 子进程可能长期持有写端。本轮改为只校验产物文件，
  不依赖进程干净退出。

**调研**：GitHub（playwright/issues #36901 等 TargetClosedError 相关 issue、
`site:github.com` 精确搜索 `CDPScreenshotNewSurface` / `CopyOutputResultSender`）
+ 全网搜索均未找到相同签名的现成 issue 或解法——**未找到现成方案，自研解决**
（对照实验 + CLI 降级；后经证伪修正根因为环境资源耗尽）。
相关参考：dev.to 上 Playwright 截图崩溃排查（/dev/shm、swap 方向，本机已排除：
/dev/shm 5.9G、内存 11G 充足）；reatom 的 Chrome 图片解码缓存笔记
（decode 预算属 EncodingError 层面，与本次 renderer 崩溃无关）。

**给自己的红队批注**：本轮前半段犯了"宣布决定性结论前未做证伪实验"的错误——
真正的对照（干净环境 × 1920×1080）只花 6 秒，我却先写了结论。五大原则里的
"对抗式审查"和"所有数据验证"不是口号：凡是"决定性"三个字出口前，
必须先跑那个能杀死自己结论的实验。

## 2026-10-01 第 20 轮：spec 多版本并存导致"漂移误报" + hssh stdin 不转发

**现象 1**：第 16–18 轮 `qa_pptx` 回读 v4 pptx 报告"字号阶梯漂移"（实际字号 20/26/…/225 vs 锁 [13,17,…,150]），但 v4 SVG 明明是按 v4 锁的字阶画的。
**根因**：`qa_pptx.find_spec_lock` 等 4 处硬编码只认 `spec_lock.md`（v3 锁，2026-09-30 前的值）；`spec_lock_v4.md`（v4 变更纪要：字阶 ×1.5 取整）躺在同一目录却从未被任何脚本读取。v4 交付物被拿 v3 锁校验 → 系统性误报。
**定位**：`qa_pptx.py fw2026-trends-v4.pptx --spec spec_lock_v4.md` 一跑即现：阶梯 84/84 合规，误报消失；真实漂移只剩主句一致性 3 页。
**解法**：新增 `scripts/spec_resolve.py` 单点治理——`resolve_spec()` 按"版本 > 基线"选择（`spec_lock_v<N>.md` 最大 N 胜出 → 回退 `spec_lock.md`；`.bak-*`/`.v2bak`/`.v3new` 等备份变体用严格正则排除，永不选中；多项目歧义返回 None 要求显式 --spec）。4 个脚本接线 + verbose 打印所用 spec 文件名（治理可见性）。
**调研**：GitHub `site:github.com` 精确搜索 spec drift / 多 spec 文件版本治理（livespec、doctrina、lazyspec、spec-sync、rag-runtime-kernel 相关仓库）+ 中文全网搜索"设计规范多版本 spec 文件并存校验拿错版本"——均为方法论/他域方案，无"同目录多版本锁文件自动选择"的现成实现——**未找到现成方案，自研解决**。

**现象 2**：`python3 scripts/check_page_map.py` 直接运行时 `from scripts.spec_resolve import` 报 ModuleNotFoundError，但 `python -m unittest` 下正常。
**根因**：直接跑脚本时 sys.path[0] 是 scripts/ 目录，`scripts` 包不可导入；只有 `svg_to_pptx.py` 有 REPO_ROOT 自举，其他脚本此前无跨脚本 import 从未暴露。
**解法**：4 脚本按既有模式补 `REPO_ROOT = Path(__file__).resolve().parent.parent; sys.path.insert(0, ...)`。教训：新增跨脚本 import 时必须同步检查所有 CLI 入口的自举。

**现象 3**：`python3 scripts/svg_to_pptx.py --help` 在无 python-pptx 环境 import 即 NameError（`_ALIGN_MAP` 模块级引用 `PP_ALIGN`），击穿了 try/except 软依赖设计。
**根因**：第 16 轮写软依赖守卫时漏了模块级字典。
**解法**：`if _PPTX_OK: _ALIGN_MAP = {...} else: _ALIGN_MAP = {}`；构建入口已有 `if not _PPTX_OK: raise RuntimeError("缺少 python-pptx")`，行为不变。新增无 pptx 模拟测试 2 个。

**现象 4（传输坑）**：`hssh omarchy 'cat > 远端文件' < 本地文件` 传过去是 0 字节空文件（md5 d41d8cd9…）。
**根因**：hssh 不转发本地 stdin 到远端命令。
**解法**：`base64 -w0` 本地编码 → 命令参数内 `echo '$B64' | base64 -d > 远端文件` → **md5 校验确认一致**（沿用第 15 轮做法）。教训：任何传输后必须 md5 回读，工具回执 ok 不等于落地。

**现象 5（诚实缺口）**：第 17 轮日志称"v4 重导出 6MB（含照片）"，但 output/ 下只有 05:01 的旧 115KB 无照片版。
**根因**：未知（导出产物未落到声称的路径，或后续被覆盖）；无 read-back 证据。
**解法**：本轮重跑导出并做三重回读（文件 6MB + qa_pptx 媒体 5893KB + 背景 PNG 像素 stddev），三证据齐才算 done。教训呼应 AGENTS.md：done = 可观测状态变化，不是日志里的一句话。

## 2026-10-01 第 21 轮：hssh 下 heredoc 完全不可用

**现象**：`hssh omarchy 'python3 - <<EOF ... EOF'` 报 `unexpected EOF while looking for matching '"'`；`hssh ... 'cat > file' <<'EOF'` 本地 heredoc 则远端收不到内容（第 20 轮现象 4 的同源问题）。
**根因**：hssh 不转发本地 stdin 到远端命令——heredoc 内容根本到不了远端，远端 shell 只看到断裂的引号。
**解法**：凡需多行脚本/文件内容，一律本地写文件 → `base64 -w0` → 命令参数内 `echo '$B64' | base64 -d > 远端路径` → md5 回读校验。单行简单命令可直接写，无需 heredoc。
**调研**：GitHub（design QA / drift report 方向：quangthai/codexkit 的 design-system-audit 把"Drift report"列为交付物、gtmbyexpedite visual-qa 等均为 checklist 方法论）+ 中文全网搜索——均为方法论/流程模板，无"spec vs SVG 主句字号漂移 HTML 报告生成器"现成实现——**未找到现成方案，自研解决**（概念参考：https://github.com/quangthai/codexkit/blob/HEAD/.codex/skills/design-system-audit/SKILL.md 的 Drift report 交付物定义）。

## 2026-10-01 第 23 轮：Wikipedia API 偶发 SSL EOF + hssh 多层引号嵌套 heredoc 炸裂

**现象 1**：`search_router.py --backends wiki` 首次真实调用报 `urlopen error [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol`，curl 同 URL 却 200，重试脚本即成功。
**根因**：瞬时网络/TLS 抖动（omarchy 出站经代理环境常见），非代码 bug——对照实验证明（curl 200 + 重试成功）。
**定位**：错误发生在 `urlopen` 握手阶段，Wikipedia API 本身正常。
**解法**：`_wiki_api_search` 对瞬时故障（URLError/SSLError/TimeoutError/ConnectionError）重试 1 次（sleep 1s）；2 次失败抛 RuntimeError，交给 search_router 的 fallback 链。HTTPError（4xx/5xx）不重试、直接抛——避免把"被限流/无结果"误当瞬时故障。
**调研**：GitHub 精确搜索 site:github.com "urlopen SSL UNEXPECTED_EOF_WHILE_READING transient retry"：kingdoooo/gmail-invoice-downloader（bounded exponential-backoff retry，HTTPError 直接重抛）与 xxsh/chip-jobs-monitor（_read_with_retry，4 次线性退避）均为同一模式，本实现与之同构；中文全网搜索"python urllib 偶发 SSL UNEXPECTED_EOF_WHILE_READING 重试解决"：结论一致（偶发抖动 → 重试；持续出现才查代理/TLS 配置）。链接：https://github.com/kingdoooo/gmail-invoice-downloader/commit/67ce58ee7b00b67420f00ab18d3b542bdd6477e7 、https://github.com/xxsh/chip-jobs-monitor/commit/9ba78dc47a558982bc866adb7ae1f6e5196adefa 。

**现象 2**：经 hssh 传 `python3 - <<'PYEOF'` 且脚本内含 `'"'"'` 式引号转义时，bash 报 `syntax error near unexpected token '('`。
**根因**：hssh 命令字符串经多层 shell 解析，heredoc + 嵌套引号转义在远端 bash 侧断裂（与"hssh 不转发 stdin"同源：复杂内联脚本不可靠）。
**解法**：重申铁律——复杂 python 脚本一律本地 `muse.write` 写文件 → `ast.parse` 验证 → base64 传输 → 远端执行。本轮后两次补丁均走此路径，一次通过。

## 2026-10-01 第 24 轮：主句一致性门禁的硬编码白名单 + 退化 fallback 静默放行

**现象**：`qa_pptx.check_role_consistency(text_map, 84)` 在"全页主句 225px、spec statement 84"的合成输入下返回 `(True, "严格对齐")`——门禁绿了，但交付物与 spec 完全偏离。
**根因**：两处。① `if expected_stmt_sz and dominant_px != expected_stmt_sz and dominant_px in (44, 56, 72)`——白名单是 v3 字阶残留，v4 的 84/225 不在其列，该分支对 v4 交付物永不触发；② `target_px = expected if expected in counts else dominant_px`——spec 期望不在实测分布中时退化为"内部一致性"，全页同错即全页"对齐"。

## 2026-10-01 第 26 轮：Commons API 三个"看似理所当然"的行为 + quote 编码冒号

**现象**：
1. `iiurlwidth=800` 请求缩略图，实返回 `960px-…` 档的 thumburl——预期 800px 落空。
2. `imageinfo` 返回的 `thumburl`/`url` 自带 `?utm_source=commons.wikimedia.org&utm_campaign=…` 跟踪参数，直接存/比对会污染去重。
3. 中文查询"针织"某条结果的 snippet 残留 `&amp;`（ImageDescription 的 HTML 实体未解）。

**根因**：
1. Thumbor 侧只有标准档位（…/500/960/1280/…），`iiurlwidth` 会被**向上取整到最近标准档**（800→960）——不是请求即所得。
2. Commons imageinfo URL 统一追加 utm 跟踪参数（analytics 用途，去掉字节相同）。
3. `extmetadata` 的文本值是 HTML 片段：`re.sub` 剥标签后仍残留实体；另附带发现 `iiprop` 未显式索取 `mime` → 返回 null。

**定位**：curl 直接调 API 对照 + 下载 thumburl、用 JPEG 头解析确认 960×1440 有效像素（宽高比正确）——行为可用，只是与直觉不符。

**最终解法**：
1. 不对抗 API：800px 只作"期望"，代码不做宽度断言，只保证 thumburl 有效（下载验证通过）。
2. 新增 `_strip_utm()`：`split("?", 1)[0]` 剥离跟踪参数。
3. 归一化时 `html.unescape(re.sub(剥标签))` 两层处理；`iiprop` 补 `|mime`。

**调研**：GitHub（fuzheado/wikipedia-ai-skills 的 wikimedia-commons-thumbnails skill、anothersava/claude-code-common 的 image-attribution 笔记）+ 全网搜索**均确认**：① "Widths round up to buckets: 640/800→960"（与本轮实测 800→960 完全吻合）；② "thumburl carries ?utm_source=… Analytics only — identical bytes come back without it"（本实现的 `_strip_utm` 与之同构）。链接：https://github.com/fuzheado/wikipedia-ai-skills/blob/HEAD/.claude/skills/wikimedia-commons-thumbnails/SKILL.md 、https://github.com/anothersava/claude-code-common/blob/HEAD/claude/learnings/wikimedia-commons-image-attribution.md 。

**附带小坑（测试期望错误）**：`urllib.parse.quote` 默认 `safe='/'`，把 Commons 文件名 `File:` 的冒号编成 `%3A`，测试断言按字面 `File:Pantone…` 写失败。根因是自写断言未先看实际值——wiki 后端同样写法（维基条目名几乎无冒号，从第 23 轮起从未暴露）。解法：不断言字面 URL，断言按实际编码写 + 注释说明；MediaWiki 对 `%3A` 解析正常，实跑链接可访问。（自写错误，无外部方案可对，搜索不适用。）

## 2026-10-02 v3 返工：svg_to_pptx 导出 PPTX 排版错乱（字号 dpi 脱节 + 宽度低估 + 换行）

**现象**：PNG 预览（SVG 直接渲染）正常，但 `svg_to_pptx.py` 导出的 PPTX 在 PowerPoint/WPS/LibreOffice 打开后文字大面积重叠错位（标题断成两行、卡片文字互压）。`qa_pptx.py` 只查结构/字号合规不查视觉还原——假阳性放行，用户实测才发现。

**根因（三层叠加）**：
1. **字号 dpi 脱节（主因）**：版式按 `sx = 13.333/1920`（144dpi）把 px 映射到英寸，字号却按固定 `PX_TO_PT = 0.75`（96dpi 假设）换算 → 字号比版式大 1.5 倍，文本框装不下。实测：72px 标题应 36pt，实际给了 54pt。
2. **宽度低估**：`text_measure.measure()` 因 `_FONT_CANDIDATES` 硬编码路径在目标机不存在 → 返回 None → 回退 `len×size×0.62`（拉丁启发式），CJK 实际字宽≈1.0em → 文本框只有需要的 ~62%。
3. **换行放大破坏**：`tf.word_wrap = True` + 单行高度文本框 → 装不下的文本换行溢出，与相邻文本框重叠成"乱码"状。

**定位过程**：LibreOffice headless 转 PDF→PNG 复现（与用户描述一致）→ 读 `build_pptx` 发现三处换算口径不一致 → 高清渲染确认"断行+重叠"模式 → 算出 1.5 倍恰为 144/96 → 因果闭环。

**最终解法**（`scripts/svg_to_pptx.py` / `text_measure.py` / `qa_pptx.py`）：
1. 字号：`px_to_pt = 72 * sx` 随版式同比例计算（`_set_run_style` 新增参数），删固定 `PX_TO_PT`；
2. 字体解析：`_resolve_font` 新增 fontconfig `fc-match` 精确解析（硬编码路径失效时的通用兜底）；
3. 启发式：CJK 感知（CJK/全角 1.0em，拉丁 0.55em）+ 15% 安全余量（渲染器字体度量差异）；
4. `tf.word_wrap = False`：SVG 文本按单行设计，宁可余量溢出不断行；
5. `qa_pptx.py` 同步修复：`check_font_ramp` 从 `ppt/presentation.xml` 读幻灯片宽度反推 `px_to_pt`（管线约定画布 1920）；`slide_text_map` 改存 px，下游 `check_role_consistency` 不再二次换算。
**验证**：1126 测试全绿（含更新的 106 个相关测试；`test_px_to_pt_constant` 曾把 0.75 写死——正是把 bug 锁进测试的反例，已改写）；修复后 PPTX 经 LibreOffice 渲染逐页目检，10 页与 SVG 设计稿一致。

**教训**：
1. 同一物理量（px→pt）在三处用两种口径，是"换算口径不一致"类 bug 的标准形状——新增换算时必须 grep 全仓库统一；
2. QA 门禁必须包含"最终产物本体渲染目检"（本次新增铁门禁：PPTX→LibreOffice→PDF→PNG 逐页比对），脚本断言通过 ≠ 用户所见正确；
3. 测试断言常量前先问"这个常量是规格还是巧合"——把 0.75 写进测试等于给 bug 上锁。
